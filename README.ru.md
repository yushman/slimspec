# slimspec

Сайт: https://yushman.github.io/slimspec/ru/

[English version](README.md)

## Сильным моделям не нужны тяжёлые спеки.

Код они читают быстро. Им нужна короткая подсказка: куда смотреть и что нельзя сломать. slimspec, плагин для Claude Code, оставляет цикл explore → plan → apply → verify и обязательный red-green TDD, но убирает горы артефактов: на изменение два временных файла, на модуль одна компактная спека во вложенном `CLAUDE.md`, который Claude Code подгружает сам.

## Установка

В Claude Code:

```
/plugin marketplace add yushman/slimspec
/plugin install slimspec@slimspec
```

Дальше: `/slimspec <идея>`

Или подключить локальный клон:

```bash
git clone https://github.com/yushman/slimspec ~/src/slimspec
claude --plugin-dir ~/src/slimspec
```

## Миграция живого проекта

Один реальный проект, просмотрщик логов на Rust с веб-интерфейсом, перевели с OpenSpec командой `/slimspec:migrate-openspec`. До и после:

|                       | OpenSpec                                    | slimspec                    |
|-----------------------|---------------------------------------------|-----------------------------|
| Спеки поведения       | 23 файла, 2 941 строка, ~155 КБ             | 3 файла, 484 строки, ~34 КБ |
| Архив изменений       | 23 изменения, 12 394 строки, ~733 КБ        | 0                           |
| Корневой `CLAUDE.md`  | 130 строк                                   | 121 строка                  |
| Файлов в `openspec/`  | 200                                         | 0                           |

### Откуда разница

- Сценарии WHEN/THEN влились в требования, которые они и описывали. Пустые разделы Purpose и шаблонные SHALL ушли.
- Одна спека на модуль вместо 23 на фичи. Агент читает только спеку модуля, в котором работает: правка в `web/` подтягивает ~11 КБ, а не россыпь capability-файлов по всему дереву.
- Архива изменений в рабочем дереве больше нет. В git-истории того проекта он остался.

### Чем пришлось заплатить

- Сценариев как списка тест-кейсов больше нет.
- Обоснования отдельных изменений пропали. Часть сохранилась в ADR, остальное есть только в git-истории.
- Самая большая спека модуля (~14 КБ) грузится целиком при любой работе в этом модуле.

Это один проект, а не бенчмарк. У вас цифры будут другими: многое зависит от того, как писались спеки.

## Как идёт работа

```
explore --gate--> plan --gate--> apply --> verify --> ground
   ^                              ^  ^        |
   |                              |  +-- fix -+   баги реализации
   |                              |           |
   +-------- refine <-------------+-----------+   вопросы к дизайну
```

`refine` правит `explore.md` и отправляет инвалидированные задачи обратно в `apply`.

- `explore`: Агент-сканер читает спеки модулей, потом код, и возвращает короткую сводку. Основная сессия задаёт вам вопросы по одному решению за раз и пишет `explore.md`. К плану сама не переходит.
- `plan`: Планировщик пишет `tasks.md` волнами и делит каждую волну на дорожки из связанных задач. Дорожки одной волны трогают непересекающиеся файлы и идут параллельно. У каждой задачи указан первый падающий тест.
- `apply`: На каждую дорожку свой исполнитель: он проходит её задачи по порядку и по каждой приносит доказательства red и green. Полный набор тестов гоняется после каждой волны.
- `verify`: Ревьюер сверяет результат с планом и дизайном, проверяет доказательства TDD и сам код. Баги уходят обратно в apply, а с вопросами к дизайну приходят к вам через `refine`.
- `ground`: Из изменения выжимается то, что стоит помнить дальше: поведение, инварианты, контракты, решения. Это вливается в спеки затронутых модулей, и сливает модель, а не поиск по ключевым словам. После этого папка изменения удаляется.

Остановок две: после explore и после plan. Дальше всё идёт само, а к вам возвращается только с вопросами агентов, замечаниями к дизайну или после двух автоматических циклов исправлений.

Все решения принимает основная сессия. Субагенты выполняют работу и возвращают короткий структурированный отчёт: статус, файлы, решения, отступления от плана, red/green. Напрямую они вас ни о чём не спрашивают. Открытый вопрос возвращается как `BLOCKED`, основная сессия задаёт его вам и перезапускает агента с ответом.

Изменение живёт в `.slimspec/changes/<slug>/`: это `explore.md` и `tasks.md`. Папка в `.gitignore` (slimspec сам добавляет `.slimspec/changes/`) и удаляется после ground. Историю хранят ваши коммиты и обновлённые спеки. `/slimspec <slug>` продолжает изменение по его файлам.

TDD во всех режимах проверяется по свидетельствам red/green; TDD-хука нет. Implementer гоняет только тесты своей задачи; полный набор тестов запускается один раз после каждой волны и ещё раз в verify.

## Режимы

| Фаза      | fast                               | medium                           | full                                   |
|-----------|------------------------------------|----------------------------------|----------------------------------------|
| `explore` | inline, ≤3 вопросов, вместе с plan | scanner + grilling               | то же + явный гейт на `explore.md`     |
| `plan`    | секция внутри `explore.md`         | агент planner, волны из дорожек  | то же + полный `tasks.md` на гейте     |
| `apply`   | один implementer, TDD              | по implementer на дорожку        | то же                                  |
| `verify`  | reviewer, глубина `low`            | reviewer, глубина `medium`       | reviewer, глубина `high`               |
| `ground`  | обновить затронутые спеки          | дистилляция + проверка намерения | то же                                  |

Planner делит каждую волну на дорожки из связанных задач с непересекающимися файлами. Apply запускает по implementer на дорожку, до `apply.agents` параллельно, и каждый проходит свои задачи по порядку.

```
/slimspec <идея>          # режим из конфига, предлагается после скана
/slimspec:fast <идея>     # фиксированный режим, без предложения
/slimspec:medium <идея>
/slimspec:full <идея>
/slimspec                 # активные изменения: продолжить или отменить
```

Каждую фазу можно вызвать и отдельно: `/slimspec:explore`, `/slimspec:plan`, `/slimspec:apply`, `/slimspec:verify`, `/slimspec:refine`, `/slimspec:ground`.

## OpenSpec, Superpowers и slimspec

slimspec многое взял у обоих. В таблице только то, что в нём сделано иначе; почему именно так, автор понял, поработав с обоими инструментами.

|                      | OpenSpec | Superpowers | slimspec |
|----------------------|----------|-------------|----------|
| Цикл                 | explore → propose → apply → verify → archive, на каждый шаг своя команда; explore и verify необязательны | brainstorming → worktree → plan → execute → завершение ветки; скиллы срабатывают сами | одна команда ведёт от explore до ground, остановки на двух гейтах |
| Артефакты изменения  | proposal, design, tasks, дельты спек; потом папка уезжает в архив в репозитории | для проекта: дизайн-документ с датой в `docs/superpowers/specs/` (коммитится) и план в `docs/superpowers/plans/`; мелкие правки согласуются в чате | `explore.md` + `tasks.md`, в `.gitignore`, удаляются после ground |
| Слияние спек         | секции ADDED / MODIFIED / REMOVED применяются к основной спеке по требованиям при архивации | в живую спеку ничего не сливается; на проект один дизайн-документ | модель вливает знания в спеку модуля, переписывает противоречия, сверяет с намерением |
| Субагенты            | встроенного механизма нет | свежий субагент на каждую задачу и ревью после неё, либо выполнение в той же сессии | scanner, planner, implementer, reviewer, grounder; структурные отчёты, вопросы поднимаются в основную сессию |
| Explore              | `/opsx:explore`, необязательный собеседник «подумать» перед proposal | brainstorming; когда дизайн проекта одобрен, следующим шагом идёт план | вопросы по одному решению за раз; план только после вашего гейта |

**В чём они сильнее.** У OpenSpec сценарии остаются явными тест-кейсами, рядом со спеками лежит полная история всех изменений, и он работает с 30+ AI-инструментами. Superpowers шире по охвату: отладка, worktree, код-ревью и другие скиллы помимо работы со спеками, причём для многих агентов. slimspec работает только с Claude Code и умеет только spec-driven цикл.

## Переезд с OpenSpec или Superpowers

```
/slimspec:migrate-openspec     # openspec/specs/ → спеки модулей
/slimspec:migrate-superpowers  # дизайн-документы Superpowers → спеки модулей
```

- Переносятся только спеки. Каждая спека источника привязывается к модулям, сжимается в ваш `spec.format` и сверяется с кодом.
- Сначала вы подтверждаете таблицу «источник → спека» и решаете по каждому утверждению, с которым расходится код.
- Изменения, планы и служебные файлы не конвертируются. Удаляются они только на финальном шаге очистки и только то, что вы подтвердите. Код не трогается.
- Сам плагин Superpowers вы удаляете через `/plugin uninstall`.

## Конфиг

Он необязателен: у каждого ключа есть значение по умолчанию. `/slimspec:init` подскажет, как запустить небольшой мастер. Тот задаёт по вопросу на ключ и записывает `.slimspec/config.yaml`:

```yaml
mode: medium              # fast | medium | full
spec:
  format: claude-md       # claude-md | readme | central | native | none
  unit: auto              # auto (по билд-файлам) | glob директорий, напр. "src/*/"
  adr: false              # дополнительно вести решения в docs/adr/NNNN-*.md
test: auto                # или явная команда
commit: none              # none | lane | wave
apply:
  agents: 3               # максимум параллельных implementer = максимум дорожек в волне
review:
  depth: auto             # auto (по режиму) | low | medium | high
models: {}                # переопределения по ролям: scanner, planner, implementer, reviewer, grounder
```

Или запустить мастер напрямую из корня проекта:

```bash
bash "<каталог плагина>/scripts/init.sh"
```

Модели по умолчанию: scanner и implementer на sonnet, planner, reviewer и grounder на opus. slimspec никогда не пушит.
