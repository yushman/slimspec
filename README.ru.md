# slimspec

Сайт: https://yushman.github.io/slimspec/ru/

[English version](README.md)

## Сильным моделям не нужны тяжёлые спеки.

Агент сам восстанавливает картину, быстро пробежав по коду. Спеке остаётся подсказать ему, что делать и где искать. А explore уже и есть спека изменения.

slimspec — плагин для Claude Code, построенный на этой идее. Он запускает цикл explore → plan → apply → verify с обязательным red-green TDD. На изменение заводятся два временных файла. У каждого модуля одна компактная спека во вложенном `CLAUDE.md`, который Claude Code подгружает автоматически: где искать и что нельзя сломать, и ничего больше.

## Установка

В Claude Code:

```
/plugin marketplace add yushman/slimspec
/plugin install slimspec@slimspec
```

Дальше: `/slimspec <идея>`

Или подключить локальный клон:

```bash
git clone https://github.com/yushman/slimspec ~/src/slimspec
claude --plugin-dir ~/src/slimspec
```

## Замеры на реальном проекте

### Миграция

Один существующий проект, просмотрщик логов на Rust с веб-интерфейсом, перевели с OpenSpec командой `/slimspec:migrate-openspec`. До и после:

|                       | OpenSpec                                    | slimspec                    |
|-----------------------|---------------------------------------------|-----------------------------|
| Спеки поведения       | 23 файла, 2 941 строка, ~155 КБ             | 3 файла, 484 строки, ~34 КБ |
| Архив изменений       | 23 изменения, 12 394 строки, ~733 КБ        | 0                           |
| Корневой `CLAUDE.md`  | 130 строк                                   | 121 строка                  |
| Файлов в `openspec/`  | 200                                         | 0                           |

### Откуда разница

- Сценарии WHEN/THEN влились в требования, которые они и описывали. Пустые разделы Purpose и шаблонные SHALL ушли.
- Одна спека на модуль вместо 23 на фичи. Агент читает только спеку модуля, в котором работает: правка в `web/` подтягивает ~11 КБ, а не россыпь capability-файлов по всему дереву.
- Архива изменений в рабочем дереве больше нет. В git-истории того проекта он остался.

### Что потеряно

- Сценариев как списка тест-кейсов больше нет.
- Обоснования отдельных изменений пропали. Часть сохранилась в ADR, остальное есть только в git-истории.
- Самая большая спека модуля (~14 КБ) грузится целиком при любой работе в этом модуле.

Спустя четыре изменения на slimspec спеки модулей — 4 файла и 641 строка, всё ещё на 78% меньше спек OpenSpec, которые они заменили.

### Стоимость изменения

Тот же проект до и после миграции, замер по транскриптам Claude Code. Токены — весь вход, который обработала модель (input + чтение кэша + запись в кэш), основная сессия и субагенты вместе. Самая близкая по размеру пара:

|                                  | OpenSpec (`logcat-padded-tags`) | slimspec full (`iana-tz-hash`) |
|----------------------------------|---------------------------------|--------------------------------|
| Изменено кода                    | 409 строк, 4 файла, один модуль | 435 строк, 15 файлов, три модуля |
| Обработано токенов               | 45,7M                           | **29,7M (−35%)**               |
| Токенов на строку кода           | ~110k                           | **~68k (−38%)**                |
| Ревью                            | нет                             | **2 раунда verify на глубине high; один реальный блокер (паника на крайних датах) исправлен внутри изменения** |
| Закоммичено процессных файлов    | ~530 строк (proposal, design, tasks, дельты спек, devlog) | **0** (папка изменения удалена; правки спек — в `CLAUDE.md` модулей) |
| Время от начала до конца, с гейтами | 91 мин                       | 56 мин                         |

При этом slimspec сделал больше: 5 вопросов по решениям и 3 гейта, 9 задач в 3 волнах, ground в 4 спеки, ADR и оба README.

Мелкие изменения показывают то же. Два изменения на OpenSpec обработали 31,5M и 45,7M токенов; два на slimspec (fast и medium) — 6,8M и 12,5M. Один implementer в OpenSpec в одиночку обрабатывал 13–16M токенов, субагент slimspec — 0–1M, потому что каждому достаётся одна узкая дорожка.

Оговорки: n = 1–2 на подход, один проект. Мелкие изменения на slimspec были в 5–10 раз меньше по коду, так что часть разницы — размер. Часть агентов slimspec работала на Sonnet или Haiku. Основная сессия прогона slimspec full несла посторонний контекст из более ранней работы, что завышает её счёт.

## Как идёт работа

```
explore --gate--> plan --gate--> apply --> verify --> ground
   ^                              ^  ^        |
   |                              |  +-- fix -+   баги реализации
   |                              |           |
   +-------- refine <-------------+-----------+   вопросы к дизайну
```

`refine` правит `explore.md` и отправляет инвалидированные задачи обратно в `apply`.

- `explore`: Агент-сканер читает спеки модулей, потом код, и возвращает короткую сводку. Основная сессия задаёт вам вопросы (одно решение на вопрос, независимые вместе) и пишет `explore.md`. К плану сама не переходит.
- `plan`: Планировщик пишет `tasks.md` волнами и делит каждую волну на дорожки из связанных задач. Дорожки одной волны трогают непересекающиеся файлы и идут параллельно. У каждой задачи указан первый падающий тест.
- `apply`: На каждую дорожку свой исполнитель: он проходит её задачи по порядку и по каждой приносит доказательства red и green. Полный набор тестов гоняется после каждой волны.
- `verify`: Ревьюер сверяет результат с планом и дизайном, проверяет доказательства TDD и сам код. Баги уходят обратно в apply, вопросы к дизайну приходят к вам через `refine`.
- `ground`: Из изменения выделяются долговременные знания (поведение, инварианты, контракты, решения), и модель вливает их в спеки затронутых модулей. Поиск по ключевым словам для слияния не используется. После этого папка изменения удаляется.

Остановок две: после explore и после plan. Каждая остановка начинается с подробного разбора: после explore показывается дизайн с диаграммами, после plan показывается полный план (волны, дорожки, тесты по задачам). Остальные фазы идут без остановок и возвращаются к вам только с вопросами агентов, замечаниями к дизайну или после двух автоматических циклов исправлений.

Все решения принимает основная сессия. Субагенты выполняют работу и возвращают короткий структурированный отчёт: статус, файлы, решения, отступления от плана, red/green. Напрямую они вас ни о чём не спрашивают. Открытый вопрос возвращается как `BLOCKED`, основная сессия задаёт его вам и перезапускает агента с ответом.

Изменение живёт в `.slimspec/changes/<slug>/`: это `explore.md` и `tasks.md`. Папка в `.gitignore` (slimspec сам добавляет `.slimspec/changes/`) и удаляется после ground. Историю хранят ваши коммиты и обновлённые спеки. `/slimspec <slug>` продолжает изменение по его файлам.

TDD во всех режимах проверяется по свидетельствам red/green; TDD-хука нет. Implementer гоняет только тесты своей задачи; полный набор тестов запускается один раз после каждой волны и ещё раз в verify.

## Режимы

| Фаза      | fast                               | medium                           | full                                   |
|-----------|------------------------------------|----------------------------------|----------------------------------------|
| `explore` | inline, ≤3 вопросов, вместе с plan | scanner + grilling               | то же + явный гейт на `explore.md`     |
| `plan`    | секция внутри `explore.md`         | агент planner, волны из дорожек  | то же + полный `tasks.md` на гейте     |
| `apply`   | один implementer, TDD              | по implementer на дорожку        | то же                                  |
| `verify`  | reviewer, глубина `low`            | reviewer, глубина `medium`       | reviewer, глубина `high`               |
| `ground`  | обновить затронутые спеки          | дистилляция + проверка намерения | то же                                  |

Planner делит каждую волну на дорожки из связанных задач с непересекающимися файлами. Apply запускает по implementer на дорожку, до `apply.agents` параллельно, и каждый проходит свои задачи по порядку.

```
/slimspec <идея>          # режим из конфига, предлагается после скана
/slimspec:fast <идея>     # фиксированный режим, без предложения
/slimspec:medium <идея>
/slimspec:full <идея>
/slimspec                 # активные изменения: продолжить или отменить
```

Каждую фазу можно вызвать и отдельно: `/slimspec:explore`, `/slimspec:plan`, `/slimspec:apply`, `/slimspec:verify`, `/slimspec:refine`, `/slimspec:ground`.

## OpenSpec, Superpowers и slimspec

slimspec использует части обоих инструментов. В таблице перечислено только то, в чём slimspec отличается; жирным в колонке slimspec выделено, в чём он лучше.

|                      | OpenSpec | Superpowers | slimspec |
|----------------------|----------|-------------|----------|
| Цикл                 | explore → propose → apply → verify → archive, на каждый шаг своя команда; explore и verify необязательны | brainstorming → worktree → plan → execute → завершение ветки; скиллы срабатывают сами | **Одна команда, две остановки.** Ведёт от explore до ground, вы останавливаетесь на двух гейтах; verify не пропускается |
| Explore              | `/opsx:explore`, необязательный собеседник «подумать» перед proposal | brainstorming; когда дизайн проекта одобрен, следующим шагом идёт план | **Explore — это и есть спека изменения.** Вопросы по одному решению записываются в `explore.md` (цель, не-цели, решения, риски); отдельных proposal и design нет |
| Артефакты изменения  | proposal, design, tasks, дельты спек; потом папка уезжает в архив в репозитории | для проекта: дизайн-документ с датой в `docs/superpowers/specs/` (коммитится) и план в `docs/superpowers/plans/`; мелкие правки согласуются в чате | **В коммит идут только код и правки спек.** `explore.md` + `tasks.md`, в `.gitignore`, удаляются после ground |
| Живая спека          | файл на capability в `openspec/specs/`, агент читает, когда вы на него укажете | нет; на проект один дизайн-документ | **Грузится сама и только там, где вы работаете.** Одна спека на модуль во вложенном `CLAUDE.md` |
| Слияние спек         | секции ADDED / MODIFIED / REMOVED применяются к основной спеке по требованиям при архивации | в живую спеку ничего не сливается | **Слияние по смыслу.** Модель переписывает противоречия и сверяет результат с намерением изменения |
| Субагенты            | встроенного механизма нет | свежий субагент на каждую задачу и ревью после неё, либо выполнение в той же сессии | **Узкие агенты, дешёвый контекст.** Scanner, planner, параллельные implementer по дорожкам, reviewer, grounder, у каждого своя модель; вопросы поднимаются к вам |
| Замеренная стоимость | 45,7M токенов на изменение ~400 строк | не замерялась | **29,7M токенов на сопоставимое изменение, с двумя раундами ревью** |

**Чего нет в slimspec.** У OpenSpec сценарии остаются явными тест-кейсами, рядом со спеками лежит полная история всех изменений, и он работает с 30+ AI-инструментами. В Superpowers есть скиллы помимо работы со спеками (отладка, worktree, код-ревью и другие), и он поддерживает многих агентов. slimspec работает только с Claude Code и покрывает только spec-driven цикл.

## Переезд с OpenSpec или Superpowers

```
/slimspec:migrate-openspec     # openspec/specs/ → спеки модулей
/slimspec:migrate-superpowers  # дизайн-документы Superpowers → спеки модулей
```

- Переносятся только спеки. Каждая спека источника привязывается к модулям, сжимается в ваш `spec.format` и сверяется с кодом.
- Сначала вы подтверждаете таблицу «источник → спека» и решаете по каждому утверждению, с которым расходится код.
- Изменения, планы и служебные файлы не конвертируются. Удаляются они только на финальном шаге очистки и только то, что вы подтвердите. Код не трогается.
- Сам плагин Superpowers удаляется через `/plugin uninstall`.

## Конфиг

Конфиг необязателен: у каждого ключа есть значение по умолчанию. `/slimspec:init` задаёт несколько вопросов в сессии и записывает `.slimspec/config.yaml`:

```yaml
mode: medium              # fast | medium | full
spec:
  format: claude-md       # claude-md | readme | central | native | none
  unit: auto              # auto (по билд-файлам) | glob директорий, напр. "src/*/"
  adr: false              # дополнительно вести решения в docs/adr/NNNN-*.md
test: auto                # или явная команда
commit: none              # none | lane | wave
apply:
  agents: 3               # максимум параллельных implementer = максимум дорожек в волне
review:
  depth: auto             # auto (по режиму) | low | medium | high
models: {}                # переопределения по ролям: scanner, planner, implementer, reviewer, grounder
```

Модели по умолчанию: scanner и implementer на sonnet, planner, reviewer и grounder на opus. slimspec никогда не пушит.
